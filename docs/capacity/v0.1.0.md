# v0.1.0 capacity evidence

This report records workload-specific, single-host measurements for release
candidate `1d85296d26466083817523ef1cf74b3cc0cf97dd`. It is reproducible evidence,
not an SLA or a production sizing promise.

## Method

- Host: Windows 11 with Docker Desktop, Docker Engine 29.8.2, Compose 5.5.1.
- Services: MySQL 8.4.11 and one API container; worker replicas varied by row.
- Limits: API 0.50 CPU/512 MiB, each worker 1.00 CPU/1 GiB, MySQL 1.50 CPU/1.5 GiB.
- Input: the repository's locked KALM corpus; 10, 50, or 100 Kubernetes
  resources per request. The measured manifest path executes OPA policy checks.
- Load: constant 3 requests/s for 10 seconds, three isolated repetitions per
  combination, with fresh volumes and a dynamic loopback port for every run.
- Accepted throughput is k6 accepted requests divided by test duration.
  Accepted P95 measures HTTP admission latency. Completion throughput is
  terminal database jobs divided by the first-create to last-finish window.
  Completion P95 measures create-to-finish latency.
- Run with `capacity/run.ps1`; raw results are intentionally excluded from Git.

## Queue recovery

Backlog recovery stopped all four workers while admitting load, then measured
drain time after restart. Crash recovery killed the only worker in flight,
waited 182 seconds for the fixed 180-second lease to expire, then restarted it.

| Scenario | Runs | Completed per run | Drain seconds | Completion P95 |
|---|---:|---:|---:|---:|
| Backlog, 4 workers, batch 100 | 3 | 30-31 | 11.318 / 11.501 / 12.239 | 13.075 / 13.746 / 16.763 s |
| Crash, 1 worker, batch 100 | 3 | 30 | 5.054 / 5.831 / 5.936 | 0.886 / 1.083 / 104.937 s |

All jobs reached a terminal state. The crash run's long tail is expected
at-least-once lease recovery, not exactly-once execution: an in-flight job can
remain unavailable for up to the 180-second lease and may be executed again.
The first crash run killed the worker before it held a job, which is why its
processing window did not include the lease delay; the other two did.

## Resource observations

Values aggregate one-second Docker samples across the 27 normal manifest runs.
Worker values are per-container samples, not the sum across replicas.

Recalculate with `python capacity/resources.py results/capacity-formal`.
The shared aggregator uses the mean of the two middle values for even sample
counts. Unrounded API memory median is 12.885 MiB; displayed values use two decimals.

| Role | Samples | CPU median | CPU peak | Memory median | Memory peak |
|---|---:|---:|---:|---:|---:|
| API | 114 | 3.87% | 17.71% | 12.88 MiB | 20.13 MiB |
| Worker | 270 | 0.47% | 100.74% | 10.23 MiB | 28.57 MiB |
| MySQL | 114 | 9.44% | 23.63% | 468.65 MiB | 497.60 MiB |

Docker can report a short CPU sample above 100% on a multi-core host. These
figures describe this constrained local run and do not predict shared-host or
managed-database behavior.

## Known limits

- The 10-second steady-load window is suitable for regression evidence, not
  soak testing, autoscaling validation, or capacity planning.
- This report does not test multi-host workers, network partitions, MySQL
  failover, registry throttling, or Trivy database outage behavior.
- Manifest request cost grows with batch content as well as resource count;
  the locked corpus is only one workload distribution.
- Crash recovery is bounded by a fixed lease. Lower recovery time requires a
  lease/heartbeat design change and a separate correctness test.
